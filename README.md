# GoF Cards

Коллекционные карточки и фэнтези-составы по фиджитал-футболу Игр Будущего 2026.
Монорепозиторий: FastAPI + Vue 3, данные подтягиваются из публичного API GoFuture.

```
gof_cards/
├── backend/     FastAPI, SQLAlchemy 2.0 (async), Alembic, pytest
├── frontend/    Vue 3 + Vite + TypeScript + Pinia, mobile first
├── shared/      constants.json — единственный источник правил и коэффициентов
└── docker-compose.yml
```

## Что реально отдаёт GoFuture API

Перед разработкой API был прозондирован. Это определило три отступления от исходного ТЗ.

| Что нужно было | Что есть в API | Решение |
|---|---|---|
| Состав из 11 игроков | Фиджитал-футбол — формат 5×5, в команде 7–8 атлетов, позиции только `Goalkeeper` и `Field player` | Состав 5 игроков: 1 вратарь + 4 полевых, 2 запасных. **Perfect XI → Perfect Five** |
| Реальные стартовые составы | `starting_lineup_team1/2` приходят пустыми во всех 28 матчах | Составы вводит администратор; до этого Perfect Five отдаёт `available: false` |
| Индивидуальная статистика игроков | `statistic` и `match_events` — `null`/пустые | Очки считаются от командного результата (`digital` / `physical` / `shootouts` / победа), поверх накладывается ручная статистика администратора |
| Рабочие ссылки на фото | Presigned-URL подписаны 22.07.2026 со сроком 24 часа и отвечают `403 Request has expired` | Картинка берётся с `/athlete/{uuid}/image/` — стабильного эндпоинта, который не протухает; бакет напрямую и подписанная ссылка остались запасными вариантами |
| Логотипы клубов | Поля с логотипом нет ни в одном ответе | Отдаются отдельным эндпоинтом `/team/{uuid}/image/`, 16 из 16 доступны |

Пустые составы и статистика — не особенность одного турнира: проверены все четыре
футбольных турнира в API (`contenders-2025`, `games-of-the-future-abu-dhabi-2025`,
`phygital-contenders-astana-2026`, `games-of-the-future-2026`) — 113 матчей, везде пусто.

Рабочие эндпоинты, которые использует синк:

- `GET /events/games-of-the-future-2026/matches/?tournament_slug=phygital-football-2026&limit=1000`
  — 28 матчей; команды и их составы вложены прямо в матчи, отдельный запрос не нужен.
- `GET /athletes/{slug}/` — позиция, игровой номер, дата рождения, фото.
- `GET /teams/{slug}/`, `GET /matches/{slug}/`, `GET /tournaments/{slug}/`.

Важно: детальные ручки работают **по slug, не по UUID** (по id — 404). Ссылки на фото —
presigned-URL Yandex Cloud с `X-Amz-Expires=86400`, поэтому они обновляются на каждом синке.

Текущий срез данных: 16 команд, 127 атлетов (20 вратарей), 28 завершённых матчей,
305 шаблонов карточек, 127 локально сохранённых фото (19 МБ).

## Зависимости и хранилище

### requirements.txt

Зависимости бэкенда закреплены в `backend/requirements.txt` (рантайм) и
`backend/requirements-dev.txt` (плюс pytest). Версии зафиксированы точно, чтобы сборка
была воспроизводимой.

```bash
# установить из файла
pip install -r backend/requirements.txt

# пересоздать файл после добавления новой библиотеки
pip freeze > backend/requirements.txt

# или аккуратнее — записать только то, что реально импортируется
pip install pipreqs && pipreqs backend --force
```

Виртуальное окружение (`.venv/`, `venv/`) **в репозиторий не попадает** — оно
платформозависимое и восстанавливается из `requirements.txt`:

```bash
python -m venv .venv
.venv/Scripts/activate          # Linux/macOS: source .venv/bin/activate
pip install -r backend/requirements.txt
```

### Постоянное хранилище /data

Всё, что должно пережить передеплой, лежит на постоянном томе `/data`:

```
/data/gof_cards.db        база SQLite
/data/media/players/      127 фотографий атлетов
/data/media/teams/        16 логотипов клубов
```

Путь задаётся в `app/core/config.py` и по умолчанию равен `/data`; переопределяется
переменной `DATA_DIR`. Если тома нет или он недоступен на запись (например, на ноутбуке
разработчика), приложение не падает, а откатывается на локальный каталог `backend/data`
и пишет об этом предупреждение в лог.

В Docker том объявлен в образе (`VOLUME ["/data"]`) и смонтирован в compose как
именованный `appdata`. Содержимое `/data` в git не коммитится: база и медиа
восстанавливаются командой `python -m scripts.manage sync`.

## Быстрый старт (локально)

```bash
# бэкенд
cd backend
python -m venv .venv && .venv/Scripts/activate      # Linux/macOS: source .venv/bin/activate
pip install -r requirements-dev.txt
python -m alembic upgrade head                       # создаст /data/gof_cards.db
python -m scripts.manage sync                        # тянет турнир, фото и логотипы в /data
python -m scripts.manage seed-bots                   # заполнит рейтинг
python -m scripts.manage create-admin admin admin@example.com adminpass1
uvicorn app.main:app --reload                        # http://localhost:8000/docs

# фронтенд
cd ../frontend
npm install
npm run dev                                          # http://localhost:5173
```

Vite проксирует `/api` на `localhost:8000`, отдельная настройка CORS для дев-режима не нужна.

### Деплой на Amvera

Конфигурация лежит в `amvera.yaml` в корне репозитория:

```yaml
meta:
  environment: python
  toolchain: { name: pip, version: "3.11" }
build:
  requirementsPath: backend/requirements.txt
  useCache: true
run:
  command: uvicorn app.main:app --host 0.0.0.0 --port 80 --app-dir backend
  containerPort: 80
  persistenceMount: /data
```

Три вещи, которые делают эту конфигурацию рабочей:

1. **Один контейнер отдаёт всё.** FastAPI обслуживает `/api`, `/docs` и `/media`, а на любой
   другой путь отдаёт собранный SPA из `frontend/dist` (history-режим). Ошибочный путь под
   `/api` или `/media` по-прежнему возвращает честный 404, а не оболочку приложения.
2. **`frontend/dist` закоммичен.** Python-окружение Amvera ставит только pip-зависимости и
   не умеет запускать npm, поэтому сборка приезжает готовой. После правок фронтенда нужно
   выполнить `npm run build` и закоммитить результат. Если предпочитаете собирать фронтенд
   на стороне платформы — переключите приложение на сборку по Dockerfile и используйте
   многоэтапный образ (заготовки лежат в `backend/Dockerfile` и `frontend/Dockerfile`).
3. **Старт не блокируется.** Первая синхронизация с GoFuture занимает пару минут и уходит в
   фон, поэтому `/health` отвечает сразу и проверка живости платформы не падает. Данные
   появляются в интерфейсе через минуту-две после первого запуска.

`persistenceMount: /data` совпадает со значением по умолчанию в коде, так что база и медиа
пишутся ровно на постоянный том. Переменную `DATA_DIR` задавать не нужно.

## Как устроена игра

**Карточки и рейтинг.** У каждой карточки есть общий рейтинг OVR и шесть характеристик.
API не публикует индивидуальную статистику, поэтому характеристики выводятся из того,
что команда реально сделала на турнире, и затеняются двумя личными фактами, которые
источник всё-таки даёт: игровым номером и датой рождения.

| Характеристика | Из чего считается |
|---|---|
| **АТК** | голы команды за матч, +4 за атакующий номер (7, 9, 10, 11, 17, 19, 20) |
| **ЗАЩ** | пропущенные за матч (инвертировано), +4 вратарю и номерам 1–6 |
| **ЦИФ** | разница мячей в цифровой части за матч |
| **ФИЗ** | разница мячей в физической части за матч |
| **ХЛД** | доля выигранных серий пенальти и глубина прохода по сетке |
| **ОПЫ** | возраст атлета и путь команды по турниру |

Метрики нормализуются по всем 16 командам на шкалу 42–97, затем складываются с весами,
разными для вратаря и полевого игрока (вратарю ЗАЩ весит 0.42, полевому АТК — 0.30).
Все веса и пороги лежат в `shared/constants.json`.

**Редкость привязана к рангу, а не к случайности.** Все 127 игроков ранжируются по OVR;
топ-10 существуют в легендарной версии, топ-32 — в эпической, топ-72 — в редкой, обычная
есть у каждого. Итого 241 шаблон игроков (127 / 72 / 32 / 10) и 64 карточки команд.
Легендарка — это действительно один из десяти лучших атлетов турнира, а не удачный ролл
на аутсайдере. Цена шаблона тоже растёт с рейтингом.

Более редкая версия одного и того же игрока читается на 1–3 пункта выше и даёт больший
множитель очков, так что обмен «моя обычная на твою эпическую» имеет смысл.

**Фото и логотипы.** Картинки не лежат ни в одном JSON-поле: `image_url` у атлета — это
протухшая presigned-ссылка, а у команды поля нет вовсе. Они отдаются собственными
эндпоинтами, которые использует и сам сайт результатов:

```
GET /api/v1.0/athlete/{uuid}/image/   ->  image/webp
GET /api/v1.0/team/{uuid}/image/      ->  image/png
```

Обратите внимание: существительное в единственном числе и **uuid**, тогда как detail-эндпоинты
тех же сущностей принимают slug. Именно поэтому логотипы поначалу выглядели отсутствующими.

Забираются 127 фото атлетов (11 МБ в webp) и **16 настоящих логотипов клубов** (756 КБ) в
`backend/media/`, отдаются с `/media`. Имя файла содержит хеш содержимого, поэтому заменённая
картинка приезжает по новому URL и не залипает в кеше браузера. Логотипы показываются на
карточках, в списке матчей и в детали игрока.

Если бейдж клуба вдруг недоступен, рисуется запасной герб: SVG-щит с монограммой,
геральдической фигурой и звёздами, детерминированный по `external_id`. На текущих данных
он не нужен ни одной команде — 16 из 16 логотипов настоящие.

**Рейтинг игроков не пуст с первого запуска.** Командой `python -m scripts.manage seed-bots`
создаются 10 заранее подготовленных аккаунтов с коллекциями и составами разной силы. Очки они
получают обычным `ScoringService` по реальным матчам, а не проставленным числом, поэтому
рейтинг сопоставим с живыми игроками. Команда идемпотентна: повторный запуск ничего не меняет.

**Бустеры и износ.** Четыре пака. При регистрации выдаётся только 1000 монет — **бесплатных
игроков нет**, состав нужно купить. В стартовом бустере гарантирован вратарь, иначе легальную
пятёрку было бы не собрать ни за какие деньги.

| Бустер | Цена | Что внутри |
|---|---|---|
| Стартовый | 200 | 5 карточек, **вратарь гарантирован** |
| Премиум | 600 | 5 карточек, минимум одна редкая |
| Легендарный | 1500 | 3 карточки, высокий шанс на эпик и легенду |
| **Коллекционный** | **3500** | 3 карточки, которые **никогда не изнашиваются** |

Обычная карточка живёт **6 турниров**: каждое участие тратит один заход у всех пяти
выставленных карточек, и после шестого она сгорает — исчезает из коллекции и из состава.
Карточка из коллекционного бустера вечная, её ресурс не расходуется. Это и делает
коллекционный пак дорогим: 3500 монет против 200 за расходный.

Интерфейс показывает ресурс полосками прямо на карточке, предупреждает перед заходом в турнир,
если что-то сгорит, и перечисляет сгоревшее в результатах прогона.

*Допущение:* «настоящие» карточки трактованы как вечные и продаются за внутриигровые монеты —
интеграцию платёжного провайдера вы ранее из MVP исключили. Если нужна покупка за реальные
деньги, меняется только источник оплаты, механика вечности уже готова.

**Обмен.** Предложение блокирует свои карточки: одна карточка не может участвовать в двух
активных предложениях сразу, иначе её удалось бы «продать» дважды. Владение перепроверяется
в момент принятия, а не только при создании. Встречное предложение закрывает исходное
(статус `COUNTERED`) и открывает зеркальное — так блокировка снимается до того, как её
займёт новое предложение. Карточка, сменившая владельца, автоматически выбывает из состава
прежнего хозяина.

**Состав.** 1 вратарь + 4 полевых + до 2 запасных, обязателен капитан (×2 очка).
Если капитан не участвовал в матче, множитель переходит к вице-капитану (×1.5).
Черновой состав хранится с `match_id = NULL`; `POST /squad/lock/{match_id}` фиксирует
слепок на конкретный матч, чтобы последующие обмены не переписывали задним числом то,
что было выставлено. При начислении очков слепок имеет приоритет над черновиком.

**Perfect Five.** Если стартовая пятёрка полностью совпала с реальной пятёркой одной
из команд — бонус +20 очков. Составы вводит администратор
(`POST /admin/matches/{id}/lineups`), поскольку API их не отдаёт.

## Турнир: ваша пятёрка в реальной сетке

Собранная команда заходит в сетку Phygital Football 2026 **на место самой слабой команды**
турнира — по нашему рейтингу это The Vicious (16-е место, 0 побед, OVR 56). Дальше сетка
играется заново, но с одним правилом: **пара, которая всё ещё совпадает с исторической,
сохраняет реальный результат**. Разыгрываются только матчи с вашим участием и те пары,
которые из-за вас изменились дальше по сетке. Так турнир остаётся тем же самым турниром,
а не абстрактной симуляцией.

Структура сетки нигде не захардкожена. Для каждого участника матча находится его предыдущий
матч — это говорит, пришёл он сюда победителем или проигравшим; команда без предыдущего матча
считается посеянной. Из данных так выводятся и GSL-группы, и перекрёстные стыковые матчи,
и плей-офф. Контрольная проверка: если не подставлять никого, движок воспроизводит все
28 матчей **с нулевым расхождением** — это покрыто тестом.

**Честная жеребьёвка.** Исход матча решает логистическая кривая на разнице рейтингов (та же
форма, что у Elo): разрыв в 14 пунктов даёт примерно 3 к 1, равные рейтинги — монетка.
Ничего не наклонено в пользу игрока. Все случайные решения прогона берутся из генератора,
засеянного одним `seed`, который сохраняется вместе с результатом, — прогон воспроизводится
в точности, поэтому исход нельзя подкрутить задним числом. Победитель определяется **до**
того, как рисуется счёт, так что счёт физически не может противоречить показанному шансу.
На 20 000 прогонов фактическая доля побед расходится с заявленной вероятностью не более
чем на 0.005, а доля серий пенальти составляет 24% против реальных 25% (7 матчей из 28).

**Один и тот же игрок может быть по обе стороны.** Карточка атлета, который выступает за
команду из сетки, спокойно играет против собственной команды — это разрешено намеренно и
проверено тестом.

**Буст пропорционален проходу.** Этапы: групповой этап → стыковой матч → четвертьфинал →
полуфинал → матч за медали → чемпион. За каждый пройденный этап начисляется 260 монет и
12 очков, плюс 60 монет и 3 очка за каждую личную победу. Взнос — 250 монет. Между
попытками действует кулдаун 60 минут: без него сильная коллекция фармила бы рейтинг
бесконечно. Все числа лежат в `shared/constants.json`, кулдаун отключается нулём.

Пример реального прогона (пятёрка OVR 77 против сетки):

```
Group C. 1st Round   FFK “ROTOR CISS GROUP”   4:1   шанс 70%   прошли
Group C. 2nd Round   Quetzales-Armadillos     2:3   шанс 16%   вылет
4th Last 16          LOS TRONCOS FC           4:5   шанс 79%   вылет
итог: стыковой матч | 1/3 | +330 монет, +27 очков
сетка: 23 матча по истории, 5 пересчитано
```

## Магазин, квесты и PWA

**Псевдо-оплата.** Покупка вечных карточек за деньги идёт через песочницу: повторяется весь
жизненный цикл настоящей интеграции — создать намерение, дождаться ответа провайдера,
выдать товар ровно один раз, — но ничего не списывается, **реквизиты карты не принимаются
и не хранятся**. В окне оплаты показаны демонстрационные реквизиты, поля не редактируются,
сверху висит плашка «ТЕСТОВЫЙ РЕЖИМ». Отдельной кнопкой моделируется отказ банка, чтобы
проверить, что при неуспехе ничего не выдаётся.

| Товар | Цена | Что выдаёт |
|---|---|---|
| Коллекционный бустер | 1990 ₸ | 3 вечные карточки |
| Три коллекционных бустера | 4990 ₸ | 9 вечных карточек |
| 10 000 монет | 990 ₸ | внутриигровая валюта |

Подмена песочницы на реального провайдера затрагивает только шаг `confirm` — он становится
обработчиком вебхука; создание платежа, идемпотентность и выдача остаются как есть.

**Квесты.** Пять заданий: посмотреть матч (раз в 6 часов), подписаться на Telegram и на
YouTube (по разу), ежедневный вход (раз в 20 часов) и привести друга. Награда за подписку
разблокируется только после перехода по ссылке, повторный сбор до истечения кулдауна
отклоняется, одноразовый квест нельзя выполнить дважды.

**Приведи друга.** У каждого аккаунта есть шестизначный код без похожих друг на друга
символов (без `O`, `I`, `0`, `1`), чтобы его можно было продиктовать. Друг вводит код при
регистрации или переходит по ссылке `/login?ref=КОД`: приглашающий получает 500 монет,
новичок — 250. Один и тот же друг засчитывается один раз, пригласить себя нельзя.

**PWA.** Приложение устанавливается на домашний экран: манифест с иконками 192 и 512
(включая maskable), `display: standalone`, стартовый экран `/collection`, ярлыки на
коллекцию, квесты и турнир. Service worker кеширует оболочку приложения и медиа, но
**никогда не кеширует API** — устаревший баланс или состав хуже честной ошибки. Иконки
сгенерированы из фирменной марки.

**Mobile first — проверено измерением.** Все девять экранов прогнаны в браузере при
320px и 390px: горизонтального переполнения нет нигде. Аудит нашёл и я починил две мелкие
зоны нажатия — логотип в шапке (26px) и кнопки капитана и удаления в слотах состава (24px);
теперь все интерактивные элементы не ниже 32px.

## Дизайн

Интерфейс собран по фирменному стилю gofuture.games. Палитра снята прямо с сайта: голубой
`#01A0EA`, фиолетовый `#7000DC` и почти чёрный фон `#070618`; фирменный градиент
`linear-gradient(135deg, #00aeff, #a443ff)` работает на кнопках, активных состояниях,
акцентных числах и полосах характеристик.

Проприетарные шрифты события (TT Fors, TT Autonomous, PHGTL) недоступны публично, поэтому
взяты ближайшие по характеру: **Space Grotesk** для заголовков и чисел, **Inter** для текста.

Что даёт дизайн-система:

- все цвета, радиусы, тени и шрифты — токены в `src/styles/main.css`, компоненты не хардкодят цвет;
- фон приложения — два мягких фирменных свечения, зафиксированных за контентом;
- поверхности стеклянные (`backdrop-filter`), рамки редкости повторяют фирменную шкалу:
  серый → голубой → фиолетовый → золото, у легендарных карточек медленный блик;
- нижняя навигация подсвечивает активную вкладку градиентной полосой и мягким ореолом;
- поле состава нарисовано с разметкой (центральный круг и линия), слоты подсвечиваются
  зелёным, если игрок совпал с реальным стартовым составом;
- состояния загрузки анимированы, всё уважает `prefers-reduced-motion`.

Флаги стран сделаны буквенными кодами, а не эмодзи: Windows не рисует
regional-indicator-символы вообще и показывает вместо флага пару букв.

Проверено вживую: экраны снимались в headless-браузере при ширине 390px. Кстати, флаг
`--window-size` в Edge headless игнорируется — реальный вьюпорт всегда 492px, поэтому
мобильные скриншоты снимались через страницу-обёртку с iframe нужной ширины.

## Начисление очков

Два слоя. Базовый считается из того, что API действительно отдаёт, — из командного
результата матча; его получает каждый закарточенный игрок этой команды:

| Событие | Очки |
|---|---|
| Участие | +2 |
| Победа / ничья | +4 / +2 |
| Гол команды в digital-части | +1 за каждый |
| Гол команды в physical-части | +1 за каждый |
| Сухой матч | +5 вратарю, +1 полевому |
| Пропущенный гол (вратарь) | −1 за каждый |
| Победа / поражение в серии пенальти | +2 / −1 |
| **Perfect Five** | **+20** |

Второй слой — ручная статистика администратора (`POST /admin/matches/{id}/stats`):
голы (+5, вратарю +8), ассисты (+3), сейвы (+1), автоголы (−2), карточки (−1 / −3).
Без неё работает только базовый слой.

Итог умножается на редкость карточки (`COMMON` 1.0 → `LEGENDARY` 1.6) и на капитанский
множитель. Все коэффициенты живут в `shared/constants.json` и меняются без правки кода.

Начисление идемпотентно: повторный `settle` переписывает запись в `points_history`
и применяет к сумме пользователя только разницу, поэтому исправление статистики
не задваивает очки.

## Что сознательно не вошло в MVP

Аукционный дом со ставками, оплата бустеров реальными деньгами и WebSocket-уведомления.
Турнир проходится за один запрос целиком — пошагового режима «матч за матчем» пока нет.
Live-обновления матчей сделаны опросом раз в 30 секунд. Эти модули отложены отдельным
этапом — на текущем турнире все 28 матчей уже завершены, live-режиму нечего показывать.
